# Business Workspace backend gap audit

**Audit date:** 18 October 2026. **Baseline:** `feat/c0-commerce-integration` at `5619fd7d67fc437dd38432199e182ef68b653a04` (before the change below). Scope is `apps/api` only. The checkout already had unrelated uncommitted Business UI, configuration, and design edits; this work did not modify them. No Linear status was used as implementation evidence.

## Decision and evidence rules

The [Business Workspace working register](https://docs.google.com/document/d/1Q3ctoI9xhy3gT6UdM4wIHZOZHFboGE6TIV9SiNnRbM4/edit), [Supplier decisions](https://docs.google.com/document/d/1AePRewwlwjdvd-dCWutYHzNi3Pp3PIpXA2sXJZZfGWU/edit), and [risk register](https://docs.google.com/document/d/1KvQfQKDLLn52IrUD5rGGbUicQXhKbybrNbR67X7UT0M/edit) were read on 18 October in signed-in Chrome. Their prose is **requirement evidence, not code proof**. The primary register labels itself a discussion draft; `APPROVED` and explicit later owner decisions govern this audit. `PROPOSED`, `OPEN`, and `DEFERRED` text is recorded as a dependency or risk, never silently promoted into a requirement. In particular, later owner direction excludes **all pharmacy ERP interaction**, confirms a single Founder Admin for MVP, and keeps any loss/cash/freshness numeric policy unset pending evidence. The risk register explicitly labels most entries recommendations or hypotheses. Its P0/P1 risk ranks do not mean implementation approval.

**Status meanings:** Implemented & Tested = endpoint/domain behavior exists and a repository test exercises it; Partial = some necessary behavior exists but a stated part is absent; Missing = no backend contract/persistence found in the searched owner modules; Unverified = code or policy cannot establish the real-world result. Tests cited below are source evidence and must be distinguished from this run's execution results in the verification section.

## Integration dependency order

1. **Supplier → sourcing:** finish safe source ingestion semantics from real CSV/XLSX samples; prove current wholesale buy cost vs retail reference, optional/unknown quantity, explicit full/partial scope, profile approval, known-SKU updates, and staged novel product review. The scoped job readback in this change permits Supplier to inspect its own persisted job; it does not parse or commit the file.
2. **Sourcing → Hub:** preserve consolidated PO line allocations, automatic qualified fallback, price/quantity exceptions, and explicit Founder distribution of scarce shared partials. Add operational request engagement only after its state/working-hours policy is specified. Keep accepted cost/quantity distinct from supplier Ready and physically accepted receipts.
3. **Hub → Delivery:** exercise real receipt/scan/print/reprint and driver barcode handoff on pilot hardware; use current custody guards and retry/return path. Delivery planning and runs remain separate concepts. Do not bridge to pharmacy ERP.
4. **Delivery → Admin:** surface verified exceptions and cash stages without equating Delivered, driver declared COD, Founder counted cash, settled collection, or supplier payable. Close an exception only through a verifiable domain outcome. Admin remains Founder only in MVP.

## Implemented slice and security assessment

**Selected first Supplier E2E blocker:** authenticated Supplier upload/job creation had no own-job readback. The change permits `GET /ingestion/jobs` and `GET /ingestion/jobs/:id` for Supplier, derives the supplier tenant from the authenticated session, scopes the database query, returns 404 for foreign/missing jobs, and keeps Admin/Hub reads. No schema or migration was needed; no supplier publish/review permission was added. The larger feed pipeline and unproven supplier price semantics are the next P0 work and must not be declared complete from this slice.

- **Security impact:** a new supplier read surface for source-job metadata and rows.
- **Trust boundary:** authenticated Supplier organization → its own ingestion jobs; Admin/Hub retain staff visibility.
- **Authorization rule:** role plus session `supplierId`, applied in SQL query; unlinked suppliers fail closed. Foreign job IDs return 404.
- **Sensitive data:** supplier source key, SKU names, prices and ingestion rows; no customer PII should enter this projection.
- **Abuse cases considered:** anonymous/customer reads, cross-supplier ID and list access, missing membership, malformed ID.
- **Security tests added:** [supplier-ingestion-readback.e2e-spec.ts](../apps/api/test/integration/supplier-ingestion-readback.e2e-spec.ts).
- **Remaining risk:** raw spreadsheet parsing, approved profile mapping, price-kind validation, and feed freshness/quantity truth remain absent.

## Verification and next action

The focused regression was observed **red** at HEAD (`GET /ingestion/jobs` as Supplier: expected 200, got 403) and **green** after the change (2/2 tests). A fresh isolated `shenacare_gap_test` database on local PostgreSQL port 55432 received all 45 migrations; no shared/development database was touched. `npm run typecheck` and `npm run build` exited 0. With `DATABASE_URL` set to that disposable database and `connection_limit=20`, full `npm test -- --forceExit` exited 0: **80/80 suites, 605 passed, 1 skipped**. An earlier full run with `connection_limit=5` exited 1 (79 passed/1 failed suites; 604 passed/1 failed/1 skipped tests) on a Prisma connection-pool timeout in `availability-resolution.e2e-spec.ts`; that suite then passed 5/5 at the larger local pool. Repository-wide `npm run lint` exited 1 with 327 errors, mostly existing `no-explicit-any`/unused-symbol findings; focused ESLint on the changed controller and new test exited 0. The touched ingestion service reports 13 lint findings on unchanged lines. The pnpm filter launcher attempted to reconcile a mixed npm/pnpm installation and failed with `EPERM`; its moved local packages were restored, without lockfile edits.

The full suite generated untracked files under `apps/api/uploads/` that were absent in the initial status. An automatic command policy rejected both scoped deletion attempts (including one explicit file), so they remain for manual cleanup. No pre-existing upload file was deleted.

**Next implementation step:** obtain one sanitized machine-readable export per supplier program and confirm wholesale buy-cost vs consumer reference-price semantics. Then implement the explicit Full Snapshot/Partial Update ingestion contract for known SKUs with unknown-quantity handling and approved mapping, test a price-only file and an out-of-order retry, and only then connect safe publication to Supplier offers. Keep novel/ambiguous products behind existing human catalog review.
